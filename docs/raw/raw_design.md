### 群聊信息提取
功能逻辑：
帮助用户提取并分析聊天记录，方便用户快速获取聊天内容和通知信息。系统自动识别微信消息，以及群公告、@所有人、接龙、投票、报名、缴费、会议、活动、截止日期等，并提取时间、地点、人物、事项、DDL等关键要素。随后，系统依照时间、主题等不同维度进行归档，对于通知按照来源、类型、优先级、待办收集信息并集中展示，形成清晰的通知总览。

用户操作流程：
在整理出群消息以后 用户可以按照下面的方式获取
1.筛选功能：可以按照时间筛选/用户指定关键词筛选
2.排序功能：AI按照时间排序 按照时间轴排列所有群聊的所有总结出来的消息 同时也可以选中一个或者多个群 对其中的消息进行时间排序 也用时间轴
3.点进一个消息以后 用户需要看到的见面包括：heading包括：AI一句话总结 + 来自哪个群 + 什么时间   正文包括：AI总结 + 所有群消息来源  

实现效果：
把碎片化信息变成清晰、可执行、可追踪的清单，避免遗漏重要信息，减少“爬楼”成本，提升群聊协作效率。让用户从繁杂消息中解放出来，真正做到重要通知一眼可见、一键可管、到期不忘。

### 正向社交和反向社交

核心是一份「人 ↔ 兴趣」的双向索引，**正向**和**反向**只是同一份数据的两个查询方向，不是两套独立逻辑：

- **正向社交**：人 → 兴趣。给定一个人，认识他的爱好，形成"人物兴趣画像"。
- **反向社交**：兴趣 → 人。给定一个爱好，找到有同样爱好的人，即"找搭子"。

分析对象是整个群的社交生态（群整体视角），但匹配范围是跨群的（全部已采集的历史群）。

#### 定位与边界

- 用户**主动查询**（输入条件 → 得到结果），不做自动监测推送。
- AI **只分析、只给建议，不执行任何动作**（不替你发消息、不替你拉群）。
- 纯个人工具，推断结果**不外露**给群成员。
- 优先级：三大功能中排第三，先做群聊梗分析和群聊信息提取。

#### 数据模型

三张核心表（或等价的图结构）：

1. **人物（person）**：群成员身份。
2. **兴趣（interest）**：自由标签，无预设分类体系。
3. **证据（evidence）**：每条兴趣标签都必须能追溯到具体的群消息，用于"打开更多"查看原文。

兴趣标注流程：

- 由 LLM 从群聊消息中**自动抽取**，每条标签必须附带证据消息。
- 抽取后**自动合并同义标签**（例如"羽毛球 / 打羽球 / 约球"归一为同一标签）。
- 支持**人工介入**：增、删、改标签（用户可纠正 LLM 的错误或补充遗漏）。

#### 匹配度计算

人-人配对的"匹配度"由以下因素构成：

- 共同兴趣标签的**数量**
- 标签的**强度/置信度加权**（被多次提到的兴趣权重更高）
- 两人在群里的**实际互动**（互相回复、@、接话）
- 发言量 / 活跃度

**不做时效衰减**：所有兴趣等权，不因时间久远而降权。

#### 产物（四类，均需实现）

1. **兴趣 → 人列表**：每个兴趣下有哪些人。
2. **人 → 兴趣列表**：某人的爱好画像。
3. **人-人配对**：两人的共同爱好 + 匹配度。
4. **组局建议**：仅输出**文字建议**，例如"可以约 A、B、C 打羽毛球"，不生成待办、不生成可直接发送的文案。

#### 前端展示（四种形态）

| 形态 | 职责 |
| --- | --- |
| 时间轴 / 事件流 | 兴趣也有首次出现时间和兴衰过程，可回放 |
| 评分卡 / 仪表盘 | 兴趣热度分、某人兴趣标签的置信度、我的社交匹配度分 |
| 人-人关系图谱 | 节点 = 人，连线 = 共同爱好，用于看出小圈层 |
| 聊天内联提示 | 在聊天上下文的消息旁直接给出兴趣提示 |

评分口径：

- **兴趣热度分**：每个爱好下的人的活跃 / 投入程度。
- **兴趣置信度**：某人在这项爱好上有多可信。
- **我的社交匹配度分**：两个都要 —— ①我 vs 每个群友的逐人匹配度（列表）；②我在群里的整体融入度（单一分数）。

#### 冷启动与未知成员

发言太少、不足以推断兴趣的成员，标为**"未知"，不做推测**；但仍然列出，并注记"未知"。

注意：这里的"仍然列出"与人-人图谱的取用规则需要确认（见下方待确认）。
