## 0. 一句话定位

把微信群里的**海量消息**变成两样东西：**清晰可执行的信息**（通知/待办）与**有生命力的群文化**（热梗/表情包/共同记忆）。

## 1. 用户场景（谁 · 什么情况 · 做什么 · 想达成什么）

| 编号 | 场景一句话 |
|---|---|
| S1 | 班级群/项目群成员**错过重要通知**时，想快速看到「最近有哪些事必须做、截止到什么时候」，而不是爬几百条楼。 |
| S2 | 群成员看到大家在刷某个梗但**不懂意思**时，想点一下就知道这个梗指什么、什么时候开始流行、谁在带头用。 |
| S3 | 群主/活跃成员想让群里的梗**变成可传播的载体**时，想把梗一键做成表情包或配文图发回群里。 |
| S4 | 想了解某个好友/群成员**是什么样的人**时，希望看到基于真实聊天行为的性格卡片，并找到和自己同频的人。**（待定稿）** |
| S5 | 想在开会/复盘前**回顾一段时间群里发生了什么**时，希望按月/按周看到梗与通知的时间轴。 |

## 2. 功能边界（做什么 / **明确不做什么**）

### 做

- 只读分析：读 wechat-cli 提供的本地数据，产出结构化分析结果。
- 三大功能的前端工作区：热梗分析、信息提取、（占位）社交图谱。
- 全流程的可视化：词云、梗卡片、时间轴、通知总览、详情抽屉。
- 异常分支的可视化：空态、失败态、低置信度、媒体缺失、无权限。

### 明确不做（写清楚比写做什么更有价值）

| 不做的事 | 原因 |
|---|---|
| **不直接读微信数据库、不处理解密** | 解密与密钥提取属于 `wechat-cli`（utils 层），前端只消费 JSON。 |
| **不写回微信**（不发消息、不清未读、不修改聊天记录） | wechat-cli 只读；产品定位「数据不出本机」。 |
| **不实现 LLM 调用与 prompt 拼装** | 属于 core 层；前端只消费 `AnalysisEnvelope`，并在界面上标注模型置信度。 |
| **不做用户账号体系 / 云端同步** | 本地工具，无登录、无上传。 |
| **本期不做移动端原生 App** | WebUI 采用响应式布局覆盖窄屏，但不打包原生。 |
| **不做聊天记录的全文浏览替代品** | 本产品是「提炼与再组织」，不是微信客户端复刻；原始消息只在通知详情里作为来源展示。 |

## 3. 信息架构与页面清单

```
聊斋 MessagePick
├── 总览 /                 → 三大功能的统一入口；今日体检
├── 热梗分析 /meme          → 功能一：词云 → 梗卡片 → 时间轴 → 再生成
├── 信息提取 /inbox         → 功能二：通知总览 / 时间轴 / 详情
├── 社交图谱 /social        → 功能三：正向 & 反向社交（占位，待定稿）
└── 数据洞察 /insight       → 统计与展示单元目录（组件复用入口）
```

**全局常驻控件**（所有页面共享，避免每个页面重复选群/选时间）：

| 控件 | 作用 | 取值 |
|---|---|---|
| 群选择器 | 多选分析范围 | 空数组 = 全部群；支持「仅群聊」快捷键 |
| 时间范围选择 | 预设 7/30/90 天 + 全部 + 自定义 | 起止倒置时自动纠正并被拦截 |
| 演示场景切换 | 走查异常分支 | 正常 / 空态 / 失败态 / 慢速 |
| 数据来源徽章 | 诚实标注 mock 或真实 | 演示数据 · mock（接口已预留） |

## 4. 页面级需求与展示形式

### 4.1 热梗分析（功能一）

| 区块 | 展示形式 | 关键信息 | 来源依据 |
|---|---|---|---|
| 指标条 | 4 张 Stat 卡 | 梗数量、提及总量、平均生命周期、存活 >30 天的梗 | 推导 |
| **词云** | **可点击词云**，字号 = 频次 | 词条 → 点击进入梗卡片 | 目标.md「可点击的词云图 -> 梗卡片」 |
| 词云布局切换 | **词云 / 热度排行 / 按出现时间** | 三种读法 | 目标.md「词云图还可以切换到按出现时间排序的形式」 |
| **梗卡片** | 卡片网格（unit） | **首次出现时间 / 最近一次调用时间 / 按时间划分的分布图** + 趋势迷你图 + 生命周期 + 贡献者 + 再生成入口 | 目标.md 明确列举 |
| **梗时间轴** | ①生命线（甘特）②热度编组 | 同一时间段什么梗在被频繁使用；一个梗从初见到无人问津经过多久 | 目标.md 原文 |
| 再生成 | 抽屉内生成区 | 表情包（多帧）等；风格可切换 | 目标.md「梗的再生成：1. 生成表情包 2. ……」 |

### 4.2 信息提取（功能二）

| 区块 | 展示形式 | 关键信息 | 来源依据 |
|---|---|---|---|
| 筛选栏 | 关键词 + 时间 + 来源群 + 类型 + 优先级 + 状态 + 只看有 DDL | 多维筛选 | 目标.md「筛选功能：时间筛选/关键词筛选」 |
| 视图切换 | **时间轴 / 卡片 / 紧凑列表** | 时间轴为默认 | 目标.md「按照时间轴排列」 |
| 排序 | 时间倒序 / 时间正序 / 优先级 / DDL 紧急度 | 可对**一个或多个群**合并排序 | 目标.md「可以选中一个或者多个群，对其中的消息进行时间排序」 |
| 通知卡片 | 卡片 unit | **heading：AI 一句话总结 + 来自哪个群 + 什么时间**；正文：AI 总结 + 来源条数 | 目标.md 详情页要求（卡片上先给概要） |
| **通知详情抽屉** | 抽屉 | heading 三要素 + AI 总结 + **所有群消息来源（按时间正序的会话流）** + 抽取要素表 + 状态流转 + 复制摘要 | 目标.md 原文逐条落实 |
| 最近到期栏 | 侧栏列表 | 按 DDL 升序 | 登记表「到期不忘」 |

### 4.3 社交关系（功能三）

> **语义已由使用者明确**（取代此前的推导草案）：
> **正向社交 = 已经熟识的人之间做了什么**（关系总结）；
> **反向社交 = 还不熟悉、但有部分兴趣爱好等相似、具备交友潜力的人**（潜力发现）。
> **具体分析口径由后端负责**，前端只按这个要求提供展示模板。

**正向社交（`forward`）— 熟人关系总结**

| 区块 | 展示形式 | 关键信息 |
|---|---|---|
| 熟人清单 | 左侧列表，按往来消息量排序 | 头像、关系标签、往来消息数、共同经历段数 |
| 关系头部 | 双头像 + `我 × TA` | 关系标签、一句话定位、置信度 |
| 关系综述 | 叙述段落 | 「这段时间你们一起做了什么」的整体描述 |
| 互动指标 | 4 个 MiniStat | 往来消息、我先开口占比、平均回复间隔、共同群聊数 |
| **共同经历** | **时间轴式列表**（带类型徽章） | 一起做过的事：一起活动 / 并肩攻坚 / 长谈 / 互相帮忙 / 庆祝；含发生时间、所在群、参与人，可展开原始消息 |
| 共同话题 / 相处感觉 | 标签云 + 情绪基调 + 互动节奏 | 共同话题、正向情绪占比、按周互动次数 |
| 维护建议 | 建议列表 | 如何把这段关系维护得更好 |

**反向社交（`reverse`）— 潜在好友发现**

| 区块 | 展示形式 | 关键信息 |
|---|---|---|
| 候选卡片 | 双列卡片，按潜力分降序 | 交友潜力分、一句话推荐理由、置信度 |
| **「为什么算非熟人」** | 独立区块（判定前提，必须可见） | 直接互动条数、最近一次互动、共同好友、判定理由 |
| 相似度对比 | **双向对比条**（上=我 / 下=TA）+ 相似度分值 | 兴趣重合、话题偏好、活跃时段、表达风格、关注议题、回复节奏（维度可扩展） |
| 共同兴趣 | 标签云 | 相似兴趣关键词 |
| 相似证据 | 可展开列表 | 双方各自说过的原话 + 时间 + 群，用于建立信任 |
| 破冰建议 | 高亮区块 | 具体可执行的开场方式 + 可切入的群 |

**性格展示卡片（两个模式共用）**：雷达图 + 趣味人格标签 + 语言风格 + 口癖 + 统计 + 置信度（登记表功能点二口径）。

## 5. 状态与异常分支（每个界面都必须能表达）

| 状态 | 触发条件 | 界面表现 |
|---|---|---|
| 加载中 | 分析进行中 | 骨架屏 + 「正在从群消息中提炼热梗…」，不阻塞其它区块 |
| 空态 | 时间范围内无消息 / 筛选过窄 / 置信度不足 | 插画式空态 + **可执行的下一步**（放宽筛选 / 换范围） |
| 失败态 | LLM 超时、core 未启动 | 错误码 + 原因 + 修复建议 + 「重新分析」按钮 |
| 未初始化 | 未执行 `wechat-cli init`，取不到密钥 | 错误码 `NOT_INITIALIZED` + 引导执行 init（待接入） |
| 低置信度 | `confidence < 0.75` | 卡片上打「置信度低」徽章，抽屉里显示百分比 |
| 媒体缺失 | `--media` 未解出图片/表情 | 占位框 + 文案说明，不显示破图 |
| 无权限 | 系统拒绝访问微信目录 | 错误码 `PERMISSION_DENIED` + 提示开启完全磁盘访问 |
| 文本放不下 | 词云空间不足 | 自动收纳到「长尾词」区域，**信息不丢失** |

## 6. 数据与规则（口径）

| 规则 | 定义 | 备注 |
|---|---|---|
| 梗计数 `count` | 该词在选定范围内的出现次数 | 与词云字号权重同源 |
| 生命周期 `lifespan_days` | `last_seen - first_seen` 的天数 | < 14 天标记「已凉」 |
| 时间分布桶 `timeline[]` | 按周聚合，`intensity` = 桶内次数 / 该梗最大桶 | 用于色阶 |
| 词云字号 | `minSize 13px → maxSize 56px`，按频次归一化后 `t^1.15` 映射 | 避免长尾词不可读 |
| 通知聚合口径 | 同一事项在群内被反复提起 → 聚合成一张卡片，`sources` 保存全部来源消息 | 详情页展示「来源归属」说明 |
| DDL 紧急度 | ≤48h = 紧急；已过期单独标识 | 前端 `deadlineHint()` |
| 消息类型枚举 | 与 wechat-cli `MSG_TYPE_FILTERS` 一一对应 | 见接口契约文档 |
| 默认值 | 群 = 全部；时间 = 全部（2026-03-01 ~ 2026-06-09 演示区间）；排序 = 时间倒序 | — |

### 首轮探针发现并修复的真实缺陷

自动化验证的价值在首轮就体现了 —— 以下 5 个缺陷此前人工截图**完全看不出来**：

1. **`useApi` 依赖数组长度动态变化**：写成 `[...deps, tick]`，React 会告警并**忽略整个依赖列表**，
   导致筛选条件变化时不重新取数 —— 即**所有筛选静默失效**。改为把依赖序列化成单个字符串。
2. **`filterNotices` 时间比较口径错误**：用展示用的 `'MM-DD HH:mm'` 与 `'YYYY-MM-DD'` 边界直接做字符串比较，
   结果时间条件把**所有条目**都过滤掉。改为独立的 `date: 'YYYY-MM-DD'` 字段比较。
