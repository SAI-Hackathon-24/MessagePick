# 目标
基于模块拆分声明，输出模块间接口契约。本阶段只做「契约」声明，不产出实现。

# 输入
docs/design/modules.md

# 输出
docs/design/api-contract.md

# 步骤
1. 阅读并理解 modules.md
2. 提问确认模糊的地方（提问未闭环时禁止产出）
3. 生成 docs/design/api-contract.md
   - 要求：每个接口都必须包含下列内容，缺一不可：
     - ID 与归属：分配 `API-###`（三位数字，永不复用），标注所属模块 `MOD-###` 与来源需求 `REQ-###`
     - 入参：字段名、类型、是否必填、约束、默认值
     - 出参：成功结构、各字段含义
     - 错误：错误码 / 错误标识、触发条件、调用方应如何处理
     - 调用关系：谁调用、谁调用它、调用时机与频率假设
     - 幂等性与重试语义：明确写「适用（策略…）」或「不适用」，不得留空
   - 总览要求：
     - 接口清单表：`API-###` / 所属 `MOD-###` / 来源 `REQ-###` / 一句话用途
     - 调用关系图（mermaid）
   - 覆盖要求：modules.md 中每个模块对外暴露的接口都必须有对应 `API-###`。
     若某个模块在本阶段未产生任何接口，必须显式列出并提问确认，不得默认省略。

# 额外要求
只声明契约，不写实现：不写函数体、不写伪代码、不选具体技术框架、不指定传输方式（HTTP/gRPC/进程内调用等一律留给后续技术设计）。
接口必须能回溯上游：无法指回某个 `MOD-###` 或 `REQ-###` 的接口，要么删除要么提问。
若 modules.md 中缺少判断接口形态所需的信息，必须提问而非假设。
不要擅自做出决定。不要揣测我的意图。有任何不清楚的地方必须通过提问的方式问清楚我。尽量调用copilot内置工具向我提问。
