# 目标
基于 PRD 与模块拆分声明，撰写高层设计（HLD）：整体架构、运行时视图、端到端关键流程与部署形态。本阶段是整条流水线中**唯一允许做技术选型**的地方。

# 输入
docs/product/prd.md
docs/design/modules.md

# 输出
docs/design/impl/high-level-design.md

# 步骤
1. 阅读并理解 prd.md 与 modules.md
2. 提问确认**约束**（提问未闭环时禁止产出）
   - 必须问清：目标运行形态（桌面端 / 扩展 / Web / 服务端 / 其他）、规模量级、部署环境、团队技术熟悉度、不可接受的方案或必须沿用的既有依赖
   - **不要逐项询问具体技术选型**：选型在第 3 步以「候选方案 + 推荐」的形式提出，由提出者确认，不由你替它决定
3. 生成 docs/design/impl/high-level-design.md
   - 要求：按模板的小节逐节填写，缺一不可：
     - 架构总览：分层、核心组件、装配关系。一张 mermaid 图 + 一段话
     - 运行时视图：进程 / 线程 / 事件循环 / 部署边界；哪些组件同进程、哪些跨进程
     - 关键流程（端到端）：挑 3–5 条最重要的用户路径，从入口走到落库，逐条写并标注覆盖的 `US-###`
     - 部署与运行形态：单机 / 客户端 / 服务端 / 插件宿主；依赖的外部服务
     - 横切关注点总览：只列清单与「是否适用」，具体机制留给 `detailed-design.md` 展开
     - 关键决策与取舍：每个决策一节，含「背景与约束 / 候选方案与取舍 / 决定 / 后果 / 上游影响」
     - 待确认：仍未闭环的问题，按 `> TODO: 待确认 —— <具体问题>` 写
   - 技术选型要求：
     - 对每个关键技术选择，给出 2–3 个候选方案、各自的取舍、你的推荐与推荐理由
     - **先把候选与推荐提交给提出者确认，确认后才写入「决定」**
     - 尚未确认的选型写在「待确认」里，不得当作已定结论写入正文
   - 追溯要求：架构总览与关键流程涉及的模块必须能指回 `MOD-###`；指不回去的要么删除要么提问
   - 上游影响要求：每个决策必须判定 `上游影响`。填了 `REQ-###` / `US-###` / `MOD-###` / `API-###` / `DM-###` 就必须**停下**，走 `design-doc-change` 回流，不允许在本文件里绕过契约层
   - 覆盖要求：modules.md 中每个 `MOD-###` 都必须在架构总览里有落点；没有落点的必须显式列出并提问

# 额外要求
本阶段是流水线中唯一允许出现框架名与技术选型的阶段：契约层（`design/` 根目录）禁止，本文件允许，且必须把选型理由写进「关键决策与取舍」。
不允许只给结论式选型：每个关键技术选择都必须列出候选方案与取舍，否则视为未完成。
不允许把未经提出者确认的选型写进「决定」栏。
未确定的事项写 `> TODO: 待确认 —— <具体问题>`，不写猜测值。
本文件只写「所有模块共用」的架构与机制；单个模块的内部实现细节不写在这里，写进对应的 `mod-###-<slug>.md`。
不得直接修改 `docs/product/`、`docs/design/`（契约层）、`docs/plan/` 下任何文档；发现上游有问题，走 `design-doc-change` 回流。
不要擅自做出决定。不要揣测我的意图。有任何不清楚的地方必须通过提问的方式问清楚我。尽量调用copilot内置工具向我提问。
