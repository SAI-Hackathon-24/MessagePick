# 目标
基于高层设计，撰写详细设计：所有模块共用的横切机制（并发 / 错误 / 存储 / 安全 / 性能 / 可观测性 / 配置 / 兼容）。

# 输入
docs/design/impl/high-level-design.md

# 输出
docs/design/impl/detailed-design.md

# 步骤
1. 阅读并理解 high-level-design.md，重点看第 5 节「横切关注点总览」——它是本文件的输入清单
2. 提问确认模糊的地方（提问未闭环时禁止产出）
   - HLD 第 5 节标为「适用」的关注点，若缺少判断机制所需的信息，必须提问而非假设
   - HLD 第 5 节标为「不适用」的关注点，必须确认这个判断仍然成立
3. 生成 docs/design/impl/detailed-design.md
   - 要求：按模板的小节逐节填写，缺一不可：
     - 并发模型：线程 / 协程 / 事件循环 / 锁的粒度；哪些操作必须串行
     - 错误处理与重试：错误分类、可重试与否、退避策略、幂等键、向用户暴露什么
     - 存储与一致性：存储选型、事务边界、缓存策略、缓存与存储的一致性口径
     - 安全与权限：认证、授权、敏感数据、输入校验边界
     - 性能与容量：目标量级、瓶颈预判、必要的优化前置条件
     - 可观测性：日志、指标、追踪；出问题时靠什么定位
     - 配置与开关：可配置项、默认值、生效时机
     - 兼容与迁移：数据 / 接口的版本演进策略、迁移路径、回滚方案
     - 关键决策与取舍：每个决策一节，含「背景与约束 / 候选方案与取舍 / 决定 / 后果 / 上游影响」
     - 待确认：仍未闭环的问题，按 `> TODO: 待确认 —— <具体问题>` 写
   - 展开要求：HLD 第 5 节标为「适用」的每一行都必须在本文件有对应小节；
     标为「不适用」的必须显式写一句理由，不得静默略过
   - 技术选型要求：同 HLD —— 列出 2–3 个候选方案 + 取舍 + 推荐理由，
     **先提交给提出者确认，确认后才写入「决定」**；未确认的写进「待确认」
   - 上游影响要求：每个决策必须判定 `上游影响`。填了条目 ID 就必须**停下**，
     走 `design-doc-change` 回流（HLD 的架构决策若被推翻，先改 HLD 再回到本文件）

# 额外要求
本文件只放**所有模块共用**的机制。任何只影响单个模块的内容不写在这里，改为提醒写进对应的 `mod-###-<slug>.md`。
不允许复述 HLD 的正文：HLD 已定的架构结论只引用，不重复描述。
不允许只给结论式选型：每个关键技术选择都必须列出候选方案与取舍，否则视为未完成。
不允许把未经提出者确认的选型写进「决定」栏。
未确定的事项写 `> TODO: 待确认 —— <具体问题>`，不写猜测值。
不得直接修改 `docs/product/`、`docs/design/`（契约层）、`docs/plan/` 下任何文档；发现上游有问题，走 `design-doc-change` 回流。
不要擅自做出决定。不要揣测我的意图。有任何不清楚的地方必须通过提问的方式问清楚我。尽量调用copilot内置工具向我提问。
