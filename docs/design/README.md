# docs/design/ —— 设计层导航

> **状态**: draft
> **上游**: `docs/product/prd.md`
> **下游**: `docs/plan/tasks.md`、`docs/design/impl/*`
> **变更中**: —
> **最后更新**: 2026-09-12

本目录分**两层**。判断一份内容该放哪层，只问一句话：

> **`design/` 根目录（契约层）回答「模块之间约定什么」；`design/impl/`（实现层）回答「模块内部怎么实现」。**

---

## 1. 契约层（本目录根）

| 文件 | 内容 | 规则 |
| --- | --- | --- |
| `modules.md` | 模块职责、边界、依赖、对外接口签名 | 只声明，不实现 |
| `api-contract.md` | 模块间接口契约（入参 / 出参 / 错误） | 只声明，不实现 |
| `data-model.md` | 数据模型与字段、约束 | 只声明，不实现 |

**禁止出现**：函数体、伪代码、具体框架名、类图、时序图、DDL。

理由：契约层是**跨模块的公共约定**。一旦被实现细节污染，模块之间就失去稳定的对接面 —— 而对接面正是「把模块分给不同人」能成立的前提。

---

## 2. 实现层（`impl/`）

| 文件 | 内容 | 谁写 |
| --- | --- | --- |
| `impl/high-level-design.md` | HLD：整体架构、分层、关键流程、运行时视图 | 架构负责人 |
| `impl/detailed-design.md` | 详设：横切机制（并发 / 错误 / 存储 / 安全 / 性能） | 架构负责人 |
| `impl/mod-###-<slug>.md` | 模块设计：内部结构、类 / 时序、状态机、决策与取舍 | **该模块负责人** |

约定：

- **一份模块设计 = 一个 `MOD-###` = 一个负责人。** 这是「把模块分派到人」的落点。
- 文件名格式 `mod-###-<slug>.md`（kebab-case，符合 `docs/README.md` §5.1），其中 `###` 必须与 `docs/design/modules.md` 中已定义的 `MOD-###` 一致。
- 模板见 `impl/mod-000-template.md`。`MOD-000` **保留给模板**，不分配给任何模块。
- 本层**允许**出现框架名、类图、时序图、代码片段 —— 与契约层相反。

---

## 3. 上游影响规则（本目录最重要的规则）

实现过程中拿到的事实，可能推翻上游设计甚至需求。因此每份实现层文档的每个「关键决策」都必须填写 `上游影响` 字段：

| `上游影响` 填什么 | 含义 | 动作 |
| --- | --- | --- |
| `无` | 纯实现细节 | 继续写 |
| `MOD-###` / `API-###` / `DM-###` | 契约变了 | **停下**，走 `design-doc-change` 回流 |
| `REQ-###` / `US-###` | **需求本身不成立或需要调整** | **停下**，走 `design-doc-change` 回流，**先改 `docs/product/prd.md`** |

**只要该字段填了条目 ID，就不允许继续往下写。**

不允许在模块设计里「绕过」PRD 就地实现 —— 验收用例是照 PRD 写的，绕过必然对不上，而且没人会发现。

回流流程见 `.github/skills/design-doc-change/SKILL.md`。

## 4. 状态

实现层文档**参与状态机**（`docs/README.md` §6）：`draft` → `reviewed` → `frozen`，修改走 `updating`。

上游 `design/*.md` 变更时，相关的 `impl/` 文档按 §7 一并进入 `updating`。

---

## 5. 实现进度不记在这里

进度记在 `docs/status/implementation.md`。它**不参与状态机** —— 高频变动的事实不该每次都触发状态流转与变更传播。
