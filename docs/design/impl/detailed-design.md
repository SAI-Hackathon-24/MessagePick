## 1. 并发模型

执行体划分与运行形态见 HLD §2 与决策 6；本节只定**串行点、锁的粒度与队列口径**。

### 1.1 执行体与允许做的事

| 执行体 | 允许 | 禁止 |
| --- | --- | --- |
| 服务进程主线程 | HTTP 入口、外壳编排（`MOD-004`）、模块查询、全部经 `MOD-002` 的读写、任务队列调度、CLI 子进程管理 | 单次同步计算 > 50 ms（大 JSON 解析、图像合成、大结果集组装） |
| worker 池（`worker_threads`） | CLI 输出解析、图像合成、大结果集组装 | 打开 SQLite、直接写媒体目录、直接回写库 |
| wechat-cli 子进程 | 每次调用即启即走 | 常驻 |
| 浏览器页面 | 渲染、交互、进度订阅（SSE）、页面内提醒检查（`REQ-046`） | 持有权威数据（每次读取都请求服务端） |

worker 的结果一律以消息回传主线程，由主线程经 `MOD-002` 落库 / 落盘（与 HLD 架构图的「回传结果」口径一致）。

### 1.2 必须串行的操作（锁的粒度）

| 串行域 | 粒度 | 机制 | 并发请求的行为 |
| --- | --- | --- | --- |
| 库写入 | 全部写入 | `MOD-002` 单一写路径，集中在主线程（`better-sqlite3` 同步接口）；不开放第二个写连接 | 同线程调用序即天然排队 |
| 采集 | 全局一把互斥锁（含分项重试） | 同一时刻最多一个采集 / 重试在跑（HLD §2） | 重复触发返回「已在采集」，入口置灰 |
| 删除 | 采集互斥锁 + 写入互斥 | 进入删除后拒绝新采集启动；采集收尾后才执行（`REQ-011`） | 删除排队等待，页面显示等待态 |
| 模型任务 | 信号量（默认 4，见 §7） | 超限 FIFO 排队；重试占用同一额度 | 排队不阻塞读缓存（HLD 决策 9） |
| 图像合成 | worker 池上限 `min(4, CPU-1)` | 按提交顺序出队 | 排队；页面显示「生成中」 |
| 提醒检查 | 页面侧定时器（默认 60 s） | 仅页面打开期间运行（HLD 决策 1 后果） | 页面关闭即停（无后台常驻） |

### 1.3 任务状态机、超时与取消

- 单任务状态：`queued → running → succeeded | failed | canceled`；批次任务（采集两来源、一批分析任务）在汇总层额外有 `partial`（部分成功）。
- 取消：仅 `queued` 可取消（出队即完成）；`running` 不提供取消——避免落半成品，靠超时兜底。
- 超时（默认值均可配，见 §7）：CLI 单命令 120 s；模型单次调用 90 s；图像合成 30 s。超时按失败处理，进入 §2 重试口径。
- 队列容量：各域队列不设硬上限（单机单用户，输入规模有限）；队列长度与进行中数量在设置页可见。

### 1.4 并发异常口径

- worker 崩溃 / 异常退出：该任务标记失败并给重试入口；主进程不受影响，已缓存内容照常可读（`REQ-016`）。
- CLI 子进程超时：强制终止后按依赖失败处理（§2.1），不读取残缺输出。
- SSE 断连：任务照常执行（服务端为权威）；页面重连后重新订阅当前进度。

## 2. 错误处理与重试

### 2.1 错误分类与可重试判定

| 类别 | 典型场景 | 自动重试 | 使用者可见动作 |
| --- | --- | --- | --- |
| 依赖未就绪 | wechat-cli 未初始化、微信客户端未运行 | 否 | 原因 + 终端操作指引 + 手动重试（HLD 决策 7） |
| 依赖瞬时失败 | CLI 命令超时 / 非零退出、网络不可达、限流、5xx | 是（§2.3） | 分项状态 + 重试按钮 |
| 配置 / 凭据错误 | 模型凭据无效、baseURL 的 DNS / TLS 层错误 | 否 | 引导到设置页（`REQ-012` 同页） |
| 本地存储错误 | DB busy、磁盘满、文件权限 | 仅 DB busy 有限重试 | 提示清理磁盘 / 检查目录权限 |
| 前置条件不满足 | 素材未确认（`REQ-014`）、未选素材档位、未配置模型 | 否 | 就地说明缺哪一步 |
| 空结果 | 筛选后无数据、某群无梗 | 不适用 | 空态 + 一键清除筛选 |

判定规则：**同一输入重放一次可能成功的 → 可重试；需要使用者先改变外部状态才能成功的 → 不可重试。**

### 2.2 错误信封（跨模块统一）

内部统一结构：`{ code, message, retryable, scope, context }`。

- `code` 复用 `docs/design/api-contract.md` 已定义的稳定错误标识集合，**不新增、不复述**；未映射的内部异常归入「未知失败」，其 `message` 不给使用者看（只进日志）。
- `scope` 标明失败边界：来源（群消息 / 通讯录）、任务引用、生成请求——分项展示与分项重试都按 `scope` 聚合（`REQ-016`）。
- 面向使用者：一句原因 + 失败边界 + 一个可执行动作（重试 / 去设置 / 终端指引）；不展示堆栈与原始报文。

### 2.3 重试与退避

- 自动重试只用于**后台任务**（采集分项、分析任务、生成）；前台点击触发的操作失败后不静默重试，直接提示 + 手动重试。
- 退避：指数 `1 s → 2 s → 4 s`，上限 30 s，叠加 ±20% 抖动；最多 3 次自动重试。
- 服务端给出 `Retry-After` / `retry_after` 时以其为准（不再叠加抖动）。
- 轻量熔断：同一目标连续 5 次可重试失败后，暂停该目标的自动重试 60 s；期间手动重试仍可用。
- 手动重试与自动重试共用同一幂等键（§2.4），只重跑失败分项，已成功分项不再执行。

### 2.4 幂等键

| 场景 | 幂等键 | 落点与效果 |
| --- | --- | --- |
| 记录写入（含重采） | 记录身份（按 `docs/design/data-model.md` 定义的记录身份字段） | `MOD-002` upsert；重复写入不新增 |
| 采集断点 | 来源 + 时间窗 + 分页游标 | 重试从失败分页继续，不重拉已入库分页 |
| 模型 / 分析任务 | 任务引用（阶段 3 裁定口径） | 结果缓存键 = 任务引用；重试命中已完成结果直接返回 |
| 生成请求 | 生成请求 ID + 变体序号 | 生成历史不重复；重复提交返回既有产出 |
| 派生结果缓存 | 输入摘要 = 数据 epoch + 任务参数 + prompt / 模板版本 | 输入未变不重算（HLD 决策 9） |

### 2.5 批次与部分失败

- 采集：两个来源各自独立记状态与结果（HLD 流程 1）；单个群失败不影响其他群；输出「成功分项 / 失败分项 + 各自原因」。
- 分析：按任务类型分项汇总；部分失败时已成功结果照常可读（先渲染缓存 + 进度 + 重试入口，HLD 决策 9）。
- 删除：不分项、不允许部分成功——见 §3.2 单事务口径，失败即整体保持原状。

## 3. 存储与一致性

存储选型与「`MOD-002` 唯一写者、事务边界 = 删除边界」见 HLD 决策 3；本节定连接、事务与缓存的具体口径。

### 3.1 连接与运行参数

- 单一写连接由服务进程主线程持有；worker 不打开库（§1.1）。
- 运行参数：`journal_mode = WAL`、`synchronous = NORMAL`、`foreign_keys = ON`、`busy_timeout = 5000 ms`。
- 读取直连同一连接（WAL 下读不阻塞写）；不引入跨进程的数据库访问。
- 任何模块不得绕过 `MOD-002` 读写库与媒体目录（HLD 架构约束）。

### 3.2 事务边界

- **一个使用者动作 = 一个事务**；不跨请求开长事务。
- 批量写入按「批」提交：单批上限 1000 行或 2 MB（先到者为限），超限拆批；批间靠幂等键（§2.4）保证可重放。
- 派生结果与其来源引用在同一事务写入；来源删除时同一事务级联删除（`REQ-011`）。
- 删除：预检（受影响实体与计数，供二次确认展示）→ 单事务内按依赖序删除库内数据（派生结果 → 原始记录 → 生成历史索引 → 媒体索引）→ 提交后按索引清理媒体文件与日志（§6）。
- 文件清理失败（被占用 / 权限）：写「待清理」标记并记录日志，下次启动重试；不因文件清理失败回滚已提交的库删除。

### 3.3 缓存策略与一致性口径

| 缓存 | 载体 | 失效口径 |
| --- | --- | --- |
| 派生结果（分析 / 生成缓存） | 库内表，经 `MOD-002` | 数据 epoch 变化、任务参数 / prompt 版本变化 |
| 进程内内存缓存（筛选选项、计数等） | 进程内存 | 进程重启即失效；任何写操作（含改判 `REQ-008`）同步失效相关键 |
| 媒体解密缓存 | 数据目录文件 + 库内索引 | 删除数据时按索引全清；**不自动淘汰**（默认无上限，提供手动清理入口） |

一致性口径：

- 权威数据只在库内；页面不做权威缓存，展示数据每次向服务端取。
- `dataEpoch`：随「更新数据完成」「删除完成」「改判落库」「迁移完成」递增；响应携带 epoch，页面丢弃过期响应（防乱序覆盖）。
- 列表与统计若同屏展示，必须取自同一 epoch、同一请求（避免数字对不上）。
- 派生结果必须携带来源引用（消息 / 梗 / 事件 ID），保证可回溯到原文（`REQ-007`）。

### 3.4 数据落点与删除覆盖

- 应用数据目录：`app.db`、`media/`、`logs/`、`config.json`、`backup/`（迁移前备份，§8）。
- 删除覆盖（`REQ-011`）：库内全部实体 + 媒体缓存 + 生成历史 + 日志；删除后回落「无数据」首屏引导（`REQ-003`）。

## 4. 安全与权限

### 4.1 网络暴露面与本地接口防护

服务仅监听回环地址（HLD §4）；但同一台机器上的其他页面仍可访问该端口，因此加一层轻量防护（按提出者确认）：

- 绑定 `127.0.0.1` / `::1`；端口默认自动选择空闲端口（§7），可配置固定端口。
- Host 校验：只接受回环 IP 与 `localhost`；Origin 校验：只接受应用页面自身 origin；不下发 CORS 头（跨源读取被浏览器默认阻断）。
- 启动令牌：每次进程启动生成 128 位随机令牌；服务端打开页面时经 URL fragment 注入；前端所有**写操作**（采集、删除、改判、生成、设置变更）必须携带令牌头；令牌只存页面内存，随进程退出失效。

### 4.2 认证与授权

- 无账号体系（单机单用户，HLD §4）：不做角色与权限模型；能访问页面即视为设备使用者本人。
- wechat-cli 需要提权的 `init` 不在应用内执行（HLD 决策 7）：应用只检测状态、给出终端指引，不请求系统权限、不做提权弹窗。

### 4.3 敏感数据口径

| 数据 | 存放 | 口径 |
| --- | --- | --- |
| 消息 / 联系人 / 媒体 | 本地数据目录 | 只在本地；不写日志；不出现在错误信息与队列状态中 |
| 模型凭据 | `config.json`（权限 0600，按提出者确认） | 界面只显示掩码与「已配置」；不进日志、不进报错文本、不回显 |
| 出站内容（模型请求） | 云端 API | 只发任务所需内容（`REQ-012` 告知口径）；按任务类型裁剪字段，不发通讯录全量、群成员全量、媒体原件等无关数据 |

### 4.4 输入校验边界

- HTTP 入参：一律 schema 校验（类型 / 长度 / 枚举 / 分页上限），非法即拒绝，不进入业务层；只收 JSON。
- CLI 输出（外部不可信输入）：逐字段校验；未知字段忽略、可选字段缺失跳过；必填缺失或类型不符 → 记日志 + 跳过该条，不落半成品。整条命令失败按 §2.1「依赖瞬时失败」处理。
- SQL：全部预编译语句 + 参数绑定，禁止字符串拼接。
- 子进程调用：`spawn` 传参数数组、不经 shell；可执行文件路径来自配置并做存在性与可执行性检查（防命令注入）。
- 浏览器渲染：使用者输入与来源消息一律走框架默认转义，不使用 `dangerouslySetInnerHTML`；不提供对外跳转 / 分享入口（`REQ-085`）。
- 文件路径：媒体 / 生成文件路径由库内相对路径解析，规范化后必须落在应用数据目录内（防路径穿越）。

## 5. 性能与容量

### 5.1 目标量级

- 数据规模：1 万–10 万条消息、5–20 个群（HLD 决策 3 背景）；单用户、单机。
- 首屏口径：按 `REQ-010` 的验收约定「数据 ≥ 1 万条、三次取中位数 < 2 s」；该耗时由服务端查询 + 本机传输 + 页面渲染三段共同决定（HLD §2）。

### 5.2 首屏预算分解

| 段 | 预算 | 手段 |
| --- | --- | --- |
| 服务端查询 | ≤ 800 ms | 覆盖索引、分页上限、派生结果预计算（HLD 决策 9） |
| 本机传输 | ≤ 200 ms | 只传首屏字段；媒体与大对象懒加载（`REQ-032` 预览走按需解密） |
| 页面渲染 | ≤ 1000 ms | 虚拟滚动（HLD 决策 2）、图表先容器后异步绘制、骨架态 |

合计控制在 2 s 以内；验收按端到端中位数，不按分段测量。

### 5.3 瓶颈预判与前置条件

| 瓶颈 | 预判 | 前置条件 |
| --- | --- | --- |
| 词云 / 图谱节点规模 | ECharts 对节点数敏感，全量渲染会卡顿 | 服务端按 top-N 截断图数据；等价表格视图（`REQ-021`、`REQ-025`）提供全量行（N 的取值属模块内，见 §11） |
| 万条级列表 | DOM 节点过多 | 虚拟滚动 + 服务端分页（UI 默认页 100 条）；禁止一次拉全量 |
| 跨群统计聚合 | 实时聚合随数据量线性变慢 | 派生结果落库；必要时建预聚合表（只经 `MOD-002`；必须能由原始数据重建） |
| CLI 大 JSON | 主线程解析阻塞服务 | 解析放 worker，按分页结果分块处理 |
| 媒体首次解密 | 首次进入媒体密集视图有等待 | 按需 + 批量 + 进度 + 重试（HLD 决策 8） |
| 冷启动 | 库打开、迁移检查、CLI 探测拖慢可用性 | 启动只做版本与依赖检查；不因分析任务阻塞可交互 |

### 5.4 查询护栏（所有模块必须遵守）

- 任何对外读取接口必须支持分页，或有显式结果上限；截断时返回截断标记与总数。
- 禁止无 `LIMIT` 的列表查询、跨请求长事务、把全量数据一次推给页面。
- 服务进程主线程不做单次 > 50 ms 的同步计算（§1.1）。

## 6. 可观测性

### 6.1 日志（唯一持久观测面）

- 形式：JSON Lines；同时输出标准输出与 `logs/app-YYYY-MM-DD.log`；按天滚动，默认保留 7 天（§7 可配）。
- 字段：`ts` / `level` / `event` / `module`（`MOD-###`）/ `requestId` / `taskRef` / `source` / `durationMs` / `code` / `counts` / `retry`。
- 禁止写入：消息原文、联系人姓名、模型凭据、启动令牌。
- 级别：`error`（需要使用者动作）/ `warn`（已自动处理、值得留存）/ `info`（动作完成）/ `debug`（默认关闭）。
- 失败时的外部输出：保留截断片段（前 4 KB）入日志；完整 CLI 原始输出转存临时文件，随日志滚动一并清理。

### 6.2 关键事件清单

| 事件 | 级别 | 用途 |
| --- | --- | --- |
| `app.start` / `app.stop` | info | 版本、数据目录、端口（停止时区分正常退出 / 异常退出） |
| `ingest.start` / `ingest.source.done` / `ingest.source.failed` / `ingest.finish` | info / error | 来源、增量范围、计数、耗时（`REQ-002` 分项状态同源） |
| `task.enqueue` / `task.start` / `task.retry` / `task.done` / `task.failed` | info / warn / error | `taskRef`、重试序号、耗时 |
| `deletion.preflight` / `deletion.done` | info | 受影响实体与计数（`REQ-011`） |
| `settings.changed` | info | 只记键名，不记值（凭据类尤其） |
| `migration.start` / `migration.done` / `migration.failed` | info / error | 版本号与备份路径（§8） |
| `cache.invalidated` | info | epoch 递增原因 |

### 6.3 定位路径

1. 页面的错误提示带 `code` 与 `requestId`；
2. 按 `requestId` 在日志检索该次请求全链路（HTTP → 任务 → worker → 存储）；
3. 按 `taskRef` 查看重试历史与最终结果；
4. 依赖类问题看 `source` 与 CLI 原始输出片段。

`requestId` 由外壳在入口生成，透传到任务、worker 与日志，是跨模块追踪的唯一载体。

### 6.4 明确不做的

- 不引入外部监控 / APM / 遥测上报（出站只允许模型调用，`REQ-085`）；
- 不做指标仪表盘：「任务进度与队列状态」是页面内交互（HLD 决策 9），不是运维指标。

## 7. 配置与开关

配置文件：应用数据目录 `config.json`，权限 0600，写入用「临时文件 + rename」原子替换；启动读取，保存后按「生效时机」生效。**解析失败**时备份为 `config.json.bad`、以默认值启动并提示（凭据缺失按未配置引导）。

## 8. 兼容与迁移

### 8.1 库结构版本与迁移

- 版本存取：`PRAGMA user_version`；目标版本 = 应用内置迁移链序号。
- 迁移脚本内置、顺序执行、只向前；每个版本一个事务，逐级提交。
- 执行时机：进程启动、打开库之后、对外提供服务之前。
- 迁移前自动备份：`backup/app.db.v<旧版本>`，保留最近 2 份；备份失败则不迁移（宁可不动）。
- 失败处理：该版本事务回滚，停止启动；日志与页面给出「已到版本 / 备份路径 / 恢复指引」。
- 回滚方案：**用备份文件替换恢复**（人工，按指引操作）；不写反向迁移脚本——反向脚本无法保证数据不丢（如已删除记录）。
- 版本过高（库由更新版本创建）：拒绝打开并提示升级应用，防止旧版写坏新结构。

### 8.2 接口兼容

- 本机 HTTP 接口不对外，前后端同包发布：不做接口版本协商，变更随发布原子生效。
- CLI 适配层（HLD 决策 7 的定位）是唯一吸收 CLI 输出变化的点：未知字段忽略、可选字段缺失跳过、必填缺失 → 该来源分项失败（§2.1）；启动日志记录 CLI 版本号，便于对账。
- 模型接口：按 OpenAI 兼容格式容错解析（未知字段忽略、可选字段缺失容错）；模型名与地址可配，不在代码写死；凭据失效 → 引导设置页（§2.1）。

### 8.3 缓存与版本

- 派生结果缓存键含输入摘要（§2.4）：数据 epoch、任务参数、prompt / 模板版本；任一项变化即失效重算，历史结果不混用。
- 生成模板库随应用内置并带版本号（HLD 决策 5）：模板更新后旧缓存不命中，历史产物不回改。
- 迁移完成后 epoch 递增，全部派生缓存失效（库结构变化可能改变结果结构）。

### 8.4 数据的可迁移性

- 备份单位 = 应用数据目录（整目录复制即可换机）；库内只存相对路径，不存绝对路径。
- 不提供应用内导入 / 导出（不新增功能）；删除不可恢复（`REQ-011`），备份责任在使用者。

## 9. 关键决策与取舍

### 决策 1 —— 长任务执行与进度回传：`worker_threads` + SSE

- **背景与约束**：HLD 决策 6 已定「服务进程编排 + 工作线程执行长任务」，但进度与结果的回传形式留给本文件；界面响应不得被任务阻塞；单用户本机、无中间网络。
- **候选方案与取舍**：① SSE：HTTP 单向推送、浏览器自动重连、实现与排障最简；本应用只需服务端→页面一个方向。② WebSocket：双向、生态成熟；本项目无双向需求，多出心跳、连接治理与代理细节。③ 轮询：实现最简单；长任务进度延迟明显、请求数放大。
- **决定**：SSE（按提出者确认）；SSE 连接建立失败时页面自动降级为 5 s 轮询。
- **后果**：进度事件统一为「任务状态变更 + 计数 + 失败边界」；页面断连不中断任务；错误经统一信封（§2.2）推送；页面重连后重新订阅（§1.4）。
- **上游影响**：无

### 决策 2 —— 并发域划分与串行点

- **背景与约束**：`MOD-002` 单写者（HLD 决策 3）；采集全局互斥、模型并发上限可配且默认值待定（HLD §2）；读路径不得排在后台队列后面（HLD 决策 9）。
- **候选方案与取舍**：① 单一全局队列串行全部任务：实现最简；采集 / 分析 / 生成互相排队，等待放大。② 分域队列 + 局部信号量（写域单写者、采集域互斥、模型域信号量、渲染 worker 池）：各域独立排队、互不阻塞；多一点调度代码。③ 不限并发：最快；易撞云端限流与写冲突。
- **决定**：②；模型任务并发默认 4（按提出者确认，可配 1–8），重试占用同一额度；渲染 worker 池上限 `min(4, CPU-1)`。
- **后果**：队列长度与进行中任务数在设置页可见；模型域排队不影响读取与已缓存内容展示。
- **上游影响**：无

### 决策 3 —— 错误分类、重试退避与幂等键

- **背景与约束**：`REQ-016` 要求失败可提示、可分项重试、已入库数据不受影响；重试不得产生重复（写入按记录身份去重、任务按引用重试）。
- **候选方案与取舍**：① 各调用点自行处理错误：直接；但重试与幂等各写一遍，语义漂移后不可测。② 统一错误信封 + 分类表 + 统一退避 + 幂等键（§2）：跨模块语义一致、可写成用例；需要各模块遵守。③ 引入任务 / 重试框架：少写代码；引入新依赖与黑盒语义，与本机单用户规模不符。
- **决定**：②；自动重试只给后台任务，指数退避 `1 s → 2 s → 4 s`（上限 30 s、±20% 抖动），最多 3 次；`Retry-After` 优先；同目标连续 5 次失败熔断 60 s。
- **后果**：前台操作不做静默重试；分项重试只重跑失败分项；错误标识复用 `docs/design/api-contract.md` 既有集合，不新增。
- **上游影响**：无

### 决策 4 —— 事务边界与缓存一致性

- **背景与约束**：HLD 决策 3 已定「事务边界 = 删除边界」；派生结果既是缓存也是数据（决策 9），需要单一权威来源；媒体是「文件 + 索引」双载体。
- **候选方案与取舍**：① 单表事务 + 代码补偿：灵活；跨表删除可能留半成品，违背 HLD 口径。② 一个使用者动作一个事务 + 文件后置清理（带待清理标记）：写入与删除都不留半成品；需要清理补偿逻辑。③ 依赖触发器 / 级联外键全自动：声明式；文件清理仍要代码，且迁移期约束管理复杂。
- **决定**：②；库内跨表用外键级联 + 单事务，文件先登记后清理；媒体缓存不自动淘汰。
- **后果**：所有模块必须经 `MOD-002` 访问数据；`dataEpoch` 作为统一失效信号（§3.3）；文件清理失败不影响库层一致性。
- **上游影响**：无

### 决策 5 —— 本地接口防护与凭据存放

- **背景与约束**：服务仅监听回环（HLD §4），无账号体系；删除不可恢复（`REQ-011`）；模型凭据必须落盘（HLD §4）。
- **候选方案与取舍**：防护：① 仅回环监听：最简；同机其他页面可盲发写请求。② Host / Origin 校验：拦住多数跨站请求；本机其他程序仍可直调。③ ② + 启动令牌（写操作必带）：防护实际生效且使用者无感；需要前端统一携带。凭据：a) `config.json` + 0600：成本最低；b) OS 钥匙串：更安全但引入原生依赖与三平台差异；c) 应用内加密：密钥仍在本机，收益有限。
- **决定**：防护取 ③，凭据取 a（均按提出者确认）。
- **后果**：启动脚本自动打开带令牌的页面；手动打开的无令牌页面为只读并给出提示；令牌随进程重启轮换、不写日志。
- **上游影响**：无

### 决策 6 —— 库迁移与回滚

- **背景与约束**：本地库随版本演进（表结构、索引、派生结果结构）；数据采集成本高、不可再生；迁移失败不能留下坏库。
- **候选方案与取舍**：① `PRAGMA user_version` + 内置顺序迁移 + 迁移前自动备份：零新依赖、可测、可恢复；无自动反向回滚。② 迁移框架（knex / drizzle 等）：生态完善；新依赖与配置成本，与单机体量不成比例。③ 手工 DDL + 文档步骤：零依赖；不可执行、易漏。
- **决定**：①（§8.1）；回滚 = 用备份恢复（人工，给出指引）；库版本高于应用时拒绝打开。
- **后果**：每次迁移前写 `backup/app.db.v<旧版本>`（保留 2 份）；迁移失败停止启动并给出恢复指引；迁移事件进日志（§6.2）。
- **上游影响**：无

### 决策 7 —— 可观测口径：结构化日志 + `requestId`

- **背景与约束**：单机工具无运维体系；排障只能靠使用者可提供的本地证据；日志又要避开敏感内容（§4.3）。
- **候选方案与取舍**：① 纯控制台输出：零落盘；页面关闭即丢，无法事后定位。② JSON 行日志落盘 + 控制台：字段稳定、可检索、易脱敏；占少量磁盘（滚动清理）。③ 结构化日志库：少写代码；本场景机制简单，多一个依赖不划算。
- **决定**：②；字段、级别、保留与清理见 §6.1；日志随「删除数据」一并清空。
- **后果**：错误提示携带 `requestId`，可按 ID 检索全链路；不引入外部监控与遥测。
- **上游影响**：无

### 决策 8 —— 性能预算与查询护栏

- **背景与约束**：`REQ-010` 为端到端口径（三段共同决定，HLD §2）；数据万条级、图表重；无预算则回归时无法定位。
- **候选方案与取舍**：① 只测端到端、事后调优：零约束；问题出现时难归因。② 分段预算 + 统一护栏（分页 / 上限 / 虚拟滚动 / worker）：事前约束各模块；需要各模块遵守份额。③ 全量预计算所有视图：首屏最快；写入与存储放大，且部分视图（生命周期类）难预计算。
- **决定**：②；预算与护栏见 §5.2 / §5.4。
- **后果**：模块内算法与数据量必须满足本预算（模块内取舍见 §11）；超预算时先启用 §5.3 的前置优化项。
- **上游影响**：无

### 决策 9 —— 启动方式：脚本拉起 + 自动打开浏览器

- **背景与约束**：HLD §2 把启动方式与打包形式留给本文件与交付阶段；形态为本机 Web（HLD 决策 1）；「记录更新至 X」与提醒是页面内状态，需要页面被打开。
- **候选方案与取舍**：① 打包为单文件可执行 + 快捷方式：交付体验最好；现在定会引入打包链路与三平台构建成本，且与设计内容无关。② Node 脚本启动（`npm start`）：拉起本机服务（含端口选择）、自动打开带令牌的浏览器页面；打包形式留交付阶段，不阻塞设计。③ 系统服务 / 开机自启：与「无后台常驻」口径冲突（HLD §2），排除。
- **决定**：②（按提出者确认）；打包形式在交付阶段定。
- **后果**：启动脚本承担「选端口 → 启服务 → 打开页面」三步；服务异常退出时脚本结束并提示查看日志（§6）。
- **上游影响**：无
